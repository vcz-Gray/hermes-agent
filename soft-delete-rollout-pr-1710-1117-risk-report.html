1. 한줄 결론

이 두 PR은 soft-delete 전환의 방향 자체는 맞고 빌드/기본 테스트도 통과했지만, 그대로 즉시 운영에 밀어 넣기엔 위험합니다. 특히 (1) 현재 코드/문서가 전제하는 deletedAt 계약과 실제 운영 기준(deletedAt: null 기본 노출)의 정합성, (2) FE 회차 목록의 카운트/페이지네이션 정합성 보정 필요, (3) apply/restore의 비원자성과 복구 범위 제한은 운영 전제와 롤아웃 순서를 엄격히 지켜야만 안전합니다.

3. 핵심 리스크

[Blocker에 가까운 Major] 실제 운영 기준이 deletedAt: null 기본 노출이라면, 현재 코드/문서 전제와 계약이 어긋나 있음

사용자 정정 기준으로 보면 deletedAt: null은 레거시 예외가 아니라 정상적으로 노출돼야 하는 기본 상태입니다. 그런데 이번 PR의 helper/문서/rollout 설명은 deletedAt 필드 부재를 active canonical처럼 다루고 있습니다.

  • BE helper: src/common/utils/visibility-query.ts:3-5, src/common/utils/public-visibility.ts:5-17
  • sitemap read-path: src/routes/sitemap/sitemap.model.ts:5-27, 40-67
  • FE public 진입 가드: src/common/utils/public-series-visibility.ts:16-45, src/pages/novel/detail/[_id].tsx:71-75
  • 문서상 선행 순서 강제: docs/soft-delete-rollout.md:13-19, 51-55
  • 정규화 적용은 apply 모드에서만 수행: src/scripts/soft-delete-rollout.job.ts:233-238

운영 의미: 리스크의 본질은 "레거시 데이터가 남아서 위험"이 아니라 현재 구현/문서가 실제 운영 계약을 잘못 가정하고 있을 수 있다는 점입니다. 만약 production truth가 정말 deletedAt: null = active라면, helper / migration / 검증 기준 / runbook 문구를 그 계약에 맞게 다시 정렬해야 합니다. 그렇지 않으면 FE sitemap 가드와 BE read-path가 함께 정상 작품 상세 404, 검색 누락, admin 기본 목록 누락을 만들 수 있습니다.

  • 관리자 회차 목록 응답을 프론트에서 후처리 필터링: src/features/admin/service/fetchers.ts:224-226
  • 회차 총개수는 여전히 seriesDetail.chapterCnt 또는 noticeData.totalCnt 사용: src/pages/studio/series-management/chapter-notice/[seriesId].tsx:132-149, 265-301
  • 동일 패턴이 스튜디오 패널에도 존재: src/features/studio/components/series-content-management-panel.tsx:71-90, 201-239

운영 의미: 이건 단순 관찰 포인트가 아니라 실제 수정해야 할 정합성 이슈입니다. 삭제 직후 마지막 페이지가 비었는데 총개수/탭 숫자/페이지 수가 그대로 남으면 운영자 입장에서는 "회차 수는 남아 있는데 목록은 비고 페이지가 튄다"는 잘못된 관리 UI가 됩니다. 즉 카운트 계산도 deleted 필터 기준과 같은 계약으로 재정렬돼야 합니다.

[Major] rollout apply / restore / creator 삭제는 비원자적일 뿐 아니라, restore 범위도 제한적임
  • rollout apply는 여러 컬렉션을 순차 업데이트하며 자동 rollback 없음: src/scripts/soft-delete-rollout.job.ts:223-248, docs/soft-delete-rollout.md:51-55
  • restore runbook도 완전복구가 아님: docs/soft-delete-restore-runbook.md:61-107, 109-187
  • creator 삭제에서 S3 프로필 이미지를 DB commit 전에 삭제: src/routes/creator/creator.service.ts:173-185

운영 의미: 중간 실패 시 데이터/파일 상태가 어긋날 수 있고, restore도 "삭제 상태만 일부 되돌리는 도구"에 가깝습니다. 구체적으로:

  • account는 inspect만 지원하고 auto-restore가 없습니다. auth/MySQL까지 얽혀 있어 별도 수동 복구가 필요합니다. (docs/soft-delete-restore-runbook.md:31-45)
  • creator는 deletedAt 해제는 가능하지만 nickname/linkInfo 원본 백업이 없으면 완전 복구가 아닙니다. (docs/soft-delete-restore-runbook.md:46-60)
  • series는 workStatus를 운영자가 명시적으로 다시 정해야 하고, comment / secondary domain은 자동 복구하지 않습니다. (docs/soft-delete-restore-runbook.md:61-83)
  • comment는 tombstone(삭제된 댓글입니다.) 상태면 원문 백업 없이는 restore apply 자체가 불가능합니다. (docs/soft-delete-restore-runbook.md:96-107)
  • secondary domain인 announcement / draft / notification / userFeedback는 기본적으로 자동 복구 범위 밖입니다. (docs/soft-delete-restore-runbook.md:183-187)

즉 이 롤아웃은 "실패해도 원복 버튼이 있는 변경"이 아니라, 백업·승인·수동 절차를 전제로 한 변경입니다.
